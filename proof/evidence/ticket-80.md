## Parent

https://github.com/lutzseverino/repository-standards/issues/79

## What to build

Build one isolated, throwaway end-to-end prototype answering: can two independent outside authors express complete standards profiles, and can the same system-owned `adopt-standards` skill apply and update them in disposable project repositories without author-specific adoption code or knowledge of the product source checkout?

Exercise the real installed CLI, filesystem, Git records, trusted author scripts, and actual fresh-agent contextual work. Use two tiny independent publisher repositories, each with defaults and contrasting complete profiles, and disposable consumers containing existing project-specific content. Keep fixtures small enough for one fresh implementation session. This ticket is the entire first proof, not the first component of a preplanned production implementation.

The parent specification is authoritative and contains the accepted product decisions and full acceptance map. Its replacement direction explicitly supersedes contrary constraints in ADR 0016, #68, and the historical resolver prototype. Provisional syntax and internal organization are design experiments; accepted decisions challenged by the evidence must be explicitly reopened.

## Acceptance criteria

- [ ] **Independent authors through one system:** Both publishers have materially different guidance and ordinary-work skills, expressed through a root `standards.yaml` referencing ordinary files. Each offers defaults and contrasting complete profiles. The same shared adoption implementation handles both without author-specific branches, adoption procedures, or hooks. Each consumer selects exactly one complete profile. The author's skills retain the Agent Skills format and cannot replace reserved system skills, including `adopt-standards`.
- [ ] **Resolution and author feedback:** Demonstrate inheritance, complete-declaration replacement, and exclusion across the two-level defaults/profile model. Verify whole-file replacement, replacement of an entire skill directory and supporting resources, and a named repository-level concern spanning files. Replacement inherits no unmentioned declaration metadata; exclusion removes associated guidance/checks/fixes. Invalid references and conflicting declarations fail with understandable, actionable explanations.
- [ ] **Read-only inspection:** Inspection exposes exact selected identity, effective inherited/replaced/excluded declarations, material, applicable operations, and prerequisites. Before/after consumer snapshots and an author-script execution trace establish that inspection neither changes the consumer nor executes author code.
- [ ] **Real shared-skill adoption:** A thin bootstrap provides first entry to the isolated installed CLI and shared skill; adoption installs repository-local pinned system skills alongside selected author skills. Actual fresh agents use the shared skill for contextual work across both publishers, using consumer-accessible inputs without inherited planning context or source-checkout knowledge. They install exact supplied content and adapt an existing project README to its real project behavior and selected guidance. Preserve prompts, tool execution records, before/after content, and the assessment of factual usefulness. A mocked agent, prewritten resulting README, or instructions for a later human do not satisfy this criterion.
- [ ] **Usable execution contract:** Applicable author fixes and checks really execute with declared ordinary runtimes/dependencies, literal argument boundaries, resolved-selection input, and inspectable results the shared skill can use. Exercise a missing prerequisite and report it before its affected operation starts, without silent installation. Record the provisional invocation/result contract and ordering demonstrated. Scripts remain trusted tooling; report declaration/result validation without claiming sandboxing or proof of arbitrary script behavior.
- [ ] **Exclusion under actual execution:** A consumer's employer-owned contribution document remains byte-for-byte unchanged through all remaining applicable operations. Execution/results establish that its excluded requirements are not enforced. Exclusion does not authorize deletion of an existing project-owned file.
- [ ] **Honest completion:** Successful adoption completes required agent work and passes applicable checks, distinguishes scripted evidence from contextual assessment, and leaves changes uncommitted. Record unchanged Git HEAD and actual working-tree changes. Later activity described by ordinary-work skills is not automatically adoption work. Incomplete runs are reported as incomplete, not successful adoption with a mandatory human checklist.
- [ ] **Retained inputs and independent pins:** Record exact tool version, immutable standards revision, and selected profile independently. In an explicit scenario-runner step after verifying adoption did not commit, commit the consumer inputs and make a fresh checkout. Remove publisher access and demonstrate ongoing use of retained content, guidance, scripts, skills, and provenance. Setup obtains and verifies the project-pinned installed CLI without copying its implementation into the consumer. Demonstrate that changing a general CLI installation does not change the project pin, routine use preserves recorded versions, and deliberate standards/tool version changes are independent.
- [ ] **Update of installed and contextual content:** Deliberately update a standards revision that changes a skill and supporting resources and guidance for a README whose project content has evolved. Show complete skill replacement, including removal of obsolete resources, and real shared-skill agent adaptation of current project-owned content. Rerun applicable checks and leave completed work uncommitted. Record the proposed treatment of previously installed content retired by a new selection; do not silently equate exclusion with permission to delete.
- [ ] **Conflict blocks the whole update:** Introduce a local edit to previously installed content. Compare against the installed baseline and establish with complete before/after consumer snapshots that the known conflict prevents all update mutation. Reconcile the intended content or profile source explicitly, then demonstrate the coherent update proceeds.
- [ ] **Failure and recovery:** Inject a failure after application has begun. Preserve actual uncommitted changes and truthful progress records; use the real agent to diagnose and retry without blindly repeating completed actions. Show successful recovery or explicitly document why the run remains incomplete. Do not fabricate recovery evidence, discard work automatically, or claim arbitrary-script rollback.
- [ ] **Inspectable proof package:** Retain an immutable Git source reference for the throwaway implementation and fixtures, a small reproducible scenario runner with focused observable assertions, exact tool/standards identities, commands and actual execution evidence, and sample consumer inputs/outputs. Map every acceptance criterion to inspectable evidence or an explicit gap. Provide a proposed public format and execution contract, unresolved decisions, limitations, and an evidence-based verdict; missing fresh-agent evidence must remain a gap. Keep scaffolding outside the production implementation path.
- [ ] **Learning reconciled before further work:** Return the verdict and acceptance-to-evidence map to #79 and reconcile findings into its specification and relevant domain/ADR documentation before any downstream production ticket is specified or marked ready. Identify accepted decisions needing reconsideration explicitly. Preserve the review-process concerns as a focused follow-up, including inherited requirements, premature readiness, backloaded evidence, and review of the final exact change. Do not treat a dependency edge or this prototype alone as their resolution.

## Boundaries

Local immutable Git publishers and an isolated CLI installation are sufficient for this deterministic proof. They do not establish public publication or GitHub-topic discoverability: record the controlled public rehearsal still required before release.

Do not implement the full redesign, create or dispatch a downstream production tree, migrate the maintainer's opinionated standards, finalize production packaging/module layout, or restore the old pack/workflow/ecosystem matrix, platform-only scripts, or fixed workflow. No profile chains, multiple selected profiles, adoption subsets, prose merging, cross-publisher component updates, marketplace, or built-in remote GitHub lifecycle is required. Do not substitute an HTML simulation or resolver-only demo for this journey.

Leave #67, closed #69, merged PR #78, and the historical prototype branch unchanged. Preserve existing unrelated dirty work. Keep #79 open and without `ready-for-agent`; only this proof ticket is initially executable. Readiness is not dispatch.
